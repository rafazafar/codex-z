# Settings styles (Tailwind CSS)

Scope: codex-z settings UI in `packages/renderer-extension/src/settings/`, mounted inside the settings Shadow DOM.

## Rules

- Use Tailwind CSS utility classes for new settings pages and components.
- Do not migrate all of `shell.css` and `accounts.css` at once. When you make major changes to a page, migrate that page and remove its old styles.
- Put reusable controls in `settings/preference-ui.ts`: grouped cards, switches, numeric inputs with units, and question-mark popovers. Use no external component library, so the Codex style remains controlled.

## Boundaries

- Use Tailwind only inside the settings Shadow DOM.
- UI injected into Codex Desktop itself, such as model pickers and Composer controls, must not use this project's Tailwind classes. Do not inject the compiled CSS into the Desktop document. Desktop uses Tailwind v4 with the same class names, `--tw-*` variables, and cascade layer names but a different theme; the two styles would override each other.

## Build

- `settings/tailwind.css` is the entry point. `shell.ts` imports it once. All settings pages share these styles.
- `scripts/tailwind-esbuild-plugin.mjs` compiles the entry point during esbuild bundling. Both the renderer build (`scripts/build.mjs`) and e2e tests that bundle renderer code must use this plugin.
- Include only Tailwind theme and utilities, without preflight. `shell.css` supplies element base styles in `@layer base`.
- The plugin declares the layer order `properties, theme, base, components, utilities`, so utilities override base styles.
- Chromium does not register `@property` inside Shadow DOM. The plugin expands its initial values into normal declarations in `@layer properties`, so ring, shadow, transform, divide, and related utilities work.
- Vitest does not compile CSS. Unit tests do not depend on style content; settings e2e tests and manual checks cover appearance.
- Tailwind is a build dependency. Compiled output enters the release package, which includes `tailwindcss-LICENSE.txt`.

## Authoring

1. Use only mapped `settings-*` colors, plus `white` and `black`. The default Tailwind palette is disabled. `--settings-*` variables select light and dark colors automatically.
2. Class names must appear as complete source strings. Do not construct them from fragments. For example, `bg-settings-${state}` is not generated by the scanner. Use variants such as `data-[state=…]:` and `group-data-[…]:`, or an object mapping of complete names.
3. The scan scope is `src/settings/` (`@source "./"` in the entry point). Add the relevant `@source` when settings UI is written in another directory.
4. Do not combine old CSS classes and Tailwind utilities on one element. Old CSS is unlayered and takes priority over utilities.
5. Put repeated controls in `preference-ui.ts`; do not copy long class lists into pages. Split new long class lists into layout, color, and state segments for readability.
6. Avoid large text blocks in settings pages. Each row should have a title, one-line description, and control. Put details in a question-mark popover. Switches use `role="switch"`; popovers use `role="tooltip"` and support hover, keyboard focus, and Esc.

## Upgrade and validation

- On Tailwind upgrades, check the output layer-order declaration and `@property` expansion, then run settings e2e tests: `renderer-idle-release.spec.ts` and `renderer-settings-accounts.spec.ts`.
